# P4. Остановка зависшей программы и лимиты

Прототип закрывает риск **R5**: «лимиты и убийство раннера ведут себя не так, как
ожидается». Он же проверяет главное обещание ADR-002 — что отдельный процесс даёт
надёжную остановку.

## Что изменилось по сравнению с планом

Планировалось проверять `setrlimit(RLIMIT_AS)` внутри раннера. От этого отказались:
лимит на адресное пространство ставится в процессе, где уже поднят ART, и способен
убить рантайм раньше пользовательского кода. Проверять гипотезу оказалось дороже,
чем обойти её.

**Лимиты соблюдает сторож в процессе IDE.** Раннер присылает свой pid сообщением
`Started` сразу после запуска; сторож опрашивает `/proc/<pid>/statm` и при превышении
времени или памяти убивает процесс. Обоснование и цена — в
[ADR-002](../adr/ADR-002-process-model.md).

## Что собрано

- Новый тип сообщения `Started` (0x07) в протоколе `:core`, с тестом на уникальность
  и разбор кодов типов.
- `RunLimits` — предел времени, предел резидентной памяти, интервал опроса.
- `ProcessStats` — чтение RSS из `/proc`, с размером страницы от системы
  (на устройствах с 16-килобайтными страницами константа 4096 врёт вчетверо).
- `AndroidPythonBackend.Handle.stop()` — остановка по кнопке, тот же путь, что и по лимиту.
- В прототипе четыре готовых примера: «привет», «вечный цикл», «ест память», «ошибка».
  Пределы в прототипе намеренно маленькие — 10 секунд и 256 МБ: ждать полминуты,
  чтобы убедиться, что сторож работает, плохой способ проверять сторожа.

## Как проверить (нужен телефон)

```bash
./gradlew :app:android:assembleDebug
adb install -r app/android/build/outputs/apk/debug/android-debug.apk
adb logcat -c && adb logcat -s eide.runner AndroidRuntime
```

### Чек-лист

1. **«вечный цикл» → Stop.** Программа останавливается, в панели строка
   `[остановлена вручную через N мс]`, **IDE продолжает работать**.
2. **«вечный цикл» без Stop.** Примерно через 10 секунд — `[снята по таймауту]`.
3. **«ест память».** Ожидается `[снята по пределу памяти]` раньше, чем система заметит
   аппетит. Самое важное здесь: **приложение целиком не должно быть убито системой**.
   Если убито — значит сторож не успевает, и порог или интервал опроса надо менять.
4. **«ошибка».** Traceback приходит в панель (в stderr), код возврата ненулевой.
5. **После любой остановки следующий Run работает.** Процесс одноразовый: каждый запуск
   получает чистый интерпретатор.
6. **Процесс действительно исчезает.** Во время работы:
   ```bash
   adb shell ps -A | grep effectnebula
   ```
   две строки; после остановки — одна.

### Что сообщить обратно

Пункты чек-листа (прошло / не прошло), и особенно — за сколько миллисекунд срабатывает
остановка по кнопке и переживает ли приложение пункт 3.

## Честно о статусе

На устройстве **не проверено**: здесь нет ни телефона, ни эмулятора. Отдельно отмечу
два места, которые именно проверкой и подтверждаются, а не рассуждением:

- `Process.killProcess` для процесса того же приложения — операция разрешённая
  (тот же UID), но полагаться на это без запуска я не готов;
- успевает ли сторож с интервалом 250 мс убить процесс, который аллоцирует по мегабайту
  в цикле, раньше системного OOM-киллера. Если нет — уменьшать интервал или порог.
