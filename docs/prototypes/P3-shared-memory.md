# P3 — разделяемая память между процессами APK

Закрывает риск R4 из плана: схема с кадрами в разделяемой памяти держится на
том, что область, созданная процессом IDE, доступна процессу раннера.

## Что проверяется

Не «работает ли `SharedMemory`» вообще — она работает, — а что она работает
**между двумя процессами одного APK**, будучи переданной через Intent, и что
кадры доходят с приемлемой частотой.

## Как проверить

1. Поставить APK, открыть вкладку **код**. В `main.py` уже лежит программа,
   рисующая ездящий квадрат.
2. Нажать **Run**. Как только программа нарисует первый кадр, IDE сама
   переключится на графику. Кнопка **Графика** — на случай, если вернулись к
   коду и хочется посмотреть снова.
3. Смотреть на экран.

## Чек-лист

| Что | Ожидание | Если не так |
|---|---|---|
| Квадрат виден | красный квадрат на тёмном фоне | кадры не доходят: смотреть logcat по тегу `eide.runner`, строка «канва недоступна» |
| Квадрат движется плавно | без рывков и мельканий | частота кадров или порядок записи в память |
| Квадрат — квадрат | не растянут | ошибка вписывания, а не программы пользователя |
| Цвет красный | не синий и не зелёный | порядок каналов; проверяется тестом, но только на хосте |
| Переключение само | после Run экран стал графическим без второй кнопки | опрос номера кадра |
| Свайп возвращает к коду | возвращает, программа продолжает | обработка жеста |
| После свайпа остаёмся в коде | графика не выскакивает обратно на следующем кадре | взвод автопоказа |
| После свайпа обратно в графику | движение продолжилось с того места | программу остановили, чего быть не должно |
| Stop останавливает | вывод «нарисовано N кадров» не появляется | штатный путь остановки |
| По окончании 600 кадров | в панели вывода «нарисовано 600 кадров» | путь завершения |

## Чего этот прототип не проверяет

**Частоту кадров численно.** На глаз «плавно» и «60 fps» — разные вещи.
Счётчик появится вместе с событиями ввода; пока достаточно ответа
«дёргается / не дёргается».

**Порядок записи в память.** Барьеры `release`/`acquire` на x86 не нужны, и
санитайзеры на десктопе их отсутствие не заметят. На ARM отсутствие барьера
даёт редкие кадры, в которых видна часть предыдущего — то есть мелькание
куском. Если такое видно, это оно, а не «телефон тормозит».

**Поведение при сворачивании приложения.** Система вправе убить раннер целиком;
обещанного поведения здесь пока нет никакого.

## Ввод: что проверять на телефоне

Кольцо событий и путь «палец → программа» проверены на десктопе целиком, включая
настоящий X-сервер и настоящую программу на Python (снимок с проведённой линией).
На Android тот же код, но события приходят от тача, а не от мыши, и это меняет две
вещи.

### Чек-лист

1. **Открыть вкладку «графика» на запущенной программе с вводом** (пример — `paint.py`
   из разбора этапа 3: рисует квадраты там, где ведёшь пальцем).
2. **Провести пальцем.** Квадраты должны идти за пальцем без заметного отставания.
3. **Провести двумя пальцами одновременно.** Оба следа должны рисоваться: у события
   есть номер указателя, и программа вправе их различать.
4. **Нажать «назад».** Должен вернуть к коду. Свайпа по холсту больше нет — он
   отдан программе, потому что горизонтальное движение не может одновременно
   рисовать и уводить с экрана. Системный жест «назад» от края — это тот же свайп,
   только не отнимающий у программы ни пикселя.
5. **Вернуться в графику.** Программа должна продолжать идти, а не начинаться заново.

### Что сообщить обратно

Отстаёт ли след от пальца заметно; рисуются ли оба следа при двух пальцах; работает
ли возврат «назад».
