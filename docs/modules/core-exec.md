# `:core` → `core.exec` — протокол IDE ↔ раннер

## Что внутри

Формат кадра и его кодек: `[u32 длина payload, big-endian][u8 тип][payload]`.
Типы сообщений — `Control`, `Stdout`, `Stderr`, `Stdin`, `FrameReady`, `Exit`;
диапазон `0x10+` зарезервирован под события отладчика (DAP).

## Почему так

Один формат на всех транспортах: локально AF_UNIX-сокет, удалённо — бинарные фреймы
WebSocket. Меняется транспорт, не протокол, поэтому удалённый бэкенд не потребует второй
реализации клиента.

Кадры графики через этот канал **не идут**: локально они лежат в разделяемой памяти, а по
сокету передаётся только уведомление `FrameReady` с индексом буфера и порядковым номером.
Отсюда скромный `MAX_PAYLOAD` в 1 МБ — если сообщение больше, значит кто-то перепутал канал,
и лучше упасть сразу, чем аллоцировать гигабайт по испорченному заголовку.

## Где грабли

- **Сокет отдаёт байты порциями.** `InputStream.read` вправе вернуть один байт вместо
  запрошенных трёх тысяч. Наивное чтение работает на `ByteArrayInputStream` и ломается на
  настоящем сокете, поэтому в тестах есть поток, отдающий ровно по одному байту.
- **`readNBytes` использовать нельзя.** Метод появился в Java 9, но на Android доступен
  только с API 33, а `minSdk` у нас 27. Такая ошибка вылезает не на сборке, а на устройстве.
  Поэтому чтение написано вручную.
- **Обрыв посреди сообщения — ошибка, а не конец потока.** `read` возвращает `null` только
  если поток закончился ровно на границе сообщения; всё остальное — `EOFException`.
