# `:core` → поиск по документу

## Что внутри

- `RopeCharSequence` — взгляд на `Rope` как на `CharSequence`, с окном.
- `SearchQuery` — что искать: строка или регулярное выражение, регистр, слово целиком.
- `TextSearch` — `findAll`, `findNext`, `findPrevious`, `replaceAll`.

## Почему понадобился отдельный взгляд на текст

Движок регулярных выражений умеет работать с `CharSequence` и ничего не знает про
деревья. Два очевидных пути оба плохи:

- отдать `rope.toString()` — значит скопировать весь документ в память ради одного
  поиска, чего мы избегали всей структурой данных;
- реализовать `charAt` через спуск по дереву — это O(log n) на каждый символ, а движок
  обращается к символам очень часто.

Поэтому окно: подряд идущие обращения обслуживает один уже вытащенный кусок, и спуск по
дереву случается раз в несколько тысяч символов. Окно выравнено по границе, кратной его
размеру, — тогда движение в любую сторону даёт предсказуемое число перезагрузок.

Цена: **взгляд не потокобезопасен**, окно это изменяемое состояние. Сам rope неизменяем,
поэтому на один текст заводится по такому взгляду на поток, и это нормально.

## Границы слова заданы явно, а не через `\b`

`\b` в Java опирается на `\w`, куда кириллица не входит без отдельного флага. Поиск слова
«шаг» с включённой опцией «слово целиком» просто не находил бы ничего. Вместо этого стоят
явные условия по `\p{L}\p{N}_`.

Это не теория: мутационная проверка подтверждает, что замена наших условий на `\b`
роняет ровно тот тест, который для этого написан.

## Доллар в замене

При обычном (не регулярном) поиске текст замены подставляется как есть. Иначе замена
«на $1 рубль» молча превратилась бы в ссылку на группу, и пользователь получил бы пустое
место вместо суммы.

## Подсветка видимой части не сканирует файл с начала

Первая редакция `matchesIn` брала ленивую последовательность всех совпадений от начала
документа и отбрасывала лишние. Лень тут не помогает: чтобы дойти до нужного места,
выражение всё равно прогоняется по всему тексту до него. Замер на файле в три мегабайта
с прокруткой в конец: **40 мс на вызов**, а вызывается он на каждом кадре, пока открыт
поиск. Это 2.5 кадра в секунду при цели в 60.

Теперь скан начинается с отступом назад от видимой области (`LOOKBEHIND`, 4096 знаков) —
**0.6 мс** на том же файле, в 66 раз меньше.

Отступ нужен для совпадения, которое началось выше экрана: без него длинное совпадение
теряло бы подсветку, стоило прокрутить на строку. Цена ограниченного отступа названа
и закреплена тестом: у совпадения длиннее 4096 знаков сообщённое `start` усечено до
начала скана. Для подсветки это незаметно, потому что отрисовка обрезает диапазон по
видимым строкам, но брать этот `start` как настоящее начало совпадения нельзя.

Тонкость, на которую есть отдельный тест: скан со смещения не должен ломать границы слова.
`Matcher.find(int)` сбрасывает область на весь текст, поэтому `(?<!...)` видит знак перед
началом скана. Наивная реализация «отрезать хвост и искать в нём» этого свойства не имеет
и находит слово внутри другого слова — мутационная проверка это подтверждает.

## Счёт совпадений возвращается одним ответом

Было два метода: `count()` и `countIsExact()`. Интерфейс звал оба, то есть проходил
по документу дважды ради одного и того же ответа. Теперь `count()` возвращает
`MatchCount(value, exact)`.

## Где грабли

- **Совпадение через границу листа.** Rope режет текст на куски, и совпадение на стыке —
  первое, что ломается при наивной работе с деревом. На это есть отдельный тест, где
  искомое лежит ровно на границе.
- **Поиск назад дороже поиска вперёд.** Регулярные выражения ищут только вперёд, поэтому
  `findPrevious` проходит совпадения с начала. Для больших документов это придётся
  переделать на поиск по блокам с конца — сейчас честно записано как известный предел.
- **`replaceAll` строит одну транзакцию.** Все замены попадают в одно действие undo, и
  откат возвращает документ целиком, а не по одному совпадению.
