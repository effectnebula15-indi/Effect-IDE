# `:core` → `project/ProjectSearch` — поиск по всем файлам

## Что делает

Обходит дерево проекта и ищет в каждом текстовом файле тем же `TextSearch`, что и
поиск внутри файла: одно регулярное выражение, одни правила про регистр и слово
целиком. Возвращает список совпадений с номером строки, колонкой и самой строкой
для показа.

## Почему не индекс

Индекс — это отдельная подсистема со своим временем жизни, инвалидацией и хранением.
Для проекта в тысячу файлов честный обход укладывается в доли секунды, а для проекта
в сто тысяч файлов эта IDE и не предназначена: потолок файла — десять мегабайт
(ADR-005).

## Ничего не знает про потоки

Ни корутин, ни диспетчеров: тот, кто зовёт, сам решает, где это исполнять, и сам
передаёт признак отмены замыканием. Иначе поиск по большому дереву невозможно
прервать — а прерывать его нужно на каждой букве в строке запроса.

## Что не читается

- **Файлы больше двух мегабайт.** Дальше это не исходники.
- **Двоичные файлы** — по нулевому байту в первых восьми килобайтах, тем же признаком,
  которым пользуется git. Способ грубый: UTF-16 без BOM он посчитает двоичным.
  Для проекта с кодом это правильный выбор, а не недосмотр — лучше пропустить редкий
  файл, чем вывалить в список мусор из середины картинки.

Обе причины считаются отдельно и попадают в результат: «просмотрено 120, пропущено 3»
честнее, чем молча укоротить список.

## Ловушка, на которую наступил тест

Первая редакция теста называла папку по-русски и падала: при `LANG=POSIX` JVM
записывает такое имя на диск вопросительными знаками — та самая ловушка
`sun.jnu.encoding` из `CLAUDE.md`, только с другой стороны. Имена файлов в тестах
теперь латиницей, а кириллица — в содержимом, где она едет байтами UTF-8 и от
локали не зависит.

Заодно это ответ на вопрос, которого никто не задавал: поиск по проекту с русскими
именами файлов на десктопе под неюникодной локалью работать не будет. Не из-за
поиска — такие файлы там вообще нельзя открыть по имени.
