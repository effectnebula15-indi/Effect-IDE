# LSP: обрамление сообщений

`core/lsp/LspWire.kt`. Это **первый кусок этапа 5**, а не работающий клиент:
здесь только нижний слой — заголовки и тело. JSON-RPC (номера запросов, ответы,
уведомления) и сам клиент — следующие.

## Что это

```
Content-Length: 128\r\n
\r\n
{"jsonrpc":"2.0", ...}
```

Своё, а не готовая библиотека: весь протокол на этом уровне — одно число в
заголовке, а тянуть ради него зависимость в `:core`, которое обязано остаться
чистым Kotlin/JVM, несоразмерно. То же рассуждение, что в ADR-006 про JGit, только
с обратным знаком: там библиотека оправдана и вынесена в свой модуль, здесь её
незачем брать вовсе.

## Два решения, из-за которых самодельные клиенты ломаются

**Читается побайтно, а не через `BufferedReader`.** Буферизованный читатель
прочитал бы заголовки вместе с куском тела и оставил бы его у себя внутри —
дальше поток читался бы как мусор. Ломается это не сразу, а когда сообщение
окажется длиннее буфера, то есть на большом файле в `didOpen`. Тест на два
сообщения подряд ловит ровно это.

**Длина — в байтах, а не в знаках.** Поэтому тело здесь `ByteArray`, а не
`String`: «привет» — это шесть знаков и двенадцать байт, и клиент, считающий
знаки, разъезжается на первом же русском слове в тексте документа.

Насколько эта ловушка настоящая, видно по тому, что **первая редакция тестов в
неё и попала**: заголовок с длиной «13» для `{"метод":1}` обрезал тело посередине,
потому что тринадцать — это знаки, а байтов там семнадцать. Тесты теперь считают
длину сами, а не берут её из головы; сырое сообщение с заведомо неверной длиной
строится отдельной функцией, чтобы такие случаи были видны глазами.

## Чего боится этот слой

- **Рассинхронизация потока.** Выдуманное `Content-Length` — это `ByteArray` на
  два гигабайта, то есть OutOfMemory вместо внятной ошибки. Потолок — шестнадцать
  мегабайт: больше любого настоящего сообщения, потому что самое большое из них —
  `didOpen` с текстом файла, а файлы ограничены десятью мегабайтами (ADR-005).
- **Чужая реализация.** Регистр имени заголовка не обещан (сравнивается без
  учёта регистра), одинокий `\n` вместо `\r\n` прощается. Падать из-за
  пропущенного `\r` дороже, чем его простить.
- **`readNBytes` нельзя.** Он появился в Java 9, а на Android доступен с API 33
  при нашем minSdk 27 — упало бы на устройстве, а не на сборке. Своя реализация,
  как и в протоколе раннера.

## Проверено

Семь мутаций, четырнадцать тестов, поток с выдачей по одному байту за вызов —
настоящий сокет ведёт себя именно так, и любая реализация, ждущая «весь заголовок
за один read», на нём разваливается.

## Чего здесь нет

JSON-RPC, клиента, запуска сервера, синхронизации документов. Отдельный вопрос,
который придётся решать прототипом, а не рассуждением: влезет ли pylsp на телефон
и с какой задержкой он отвечает. Пока этого нет, этап 5 не начат по существу.
