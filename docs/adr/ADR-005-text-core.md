# ADR-005. Ядро текста: персистентный rope из чанков UTF-16

## Контекст

Потолок размера файла — 10 МБ (требование 100 МБ снято владельцем проекта). Подсветка
(tree-sitter) и LSP работают в фоновом потоке, пока пользователь продолжает печатать.

## Решение

Персистентный rope: неизменяемое AVL-сбалансированное дерево, данные в листьях,
лист до 1024 UTF-16 code units. Узлы хранят суммарную длину и число переносов строк, поэтому
позиция по офсету и по номеру строки находится за O(log n).

## Почему rope, а не piece table

Решающий довод — не скорость правки, а снимки. Фоновому парсеру нужен неизменяемый снимок
документа. Персистентный rope отдаёт его за O(1): держим ссылку на прежний корень, правка
создаёт новые узлы только вдоль одного пути. С piece table это достижимо, но сложнее.

Главное преимущество piece table — не читать файл целиком с диска — вместе с требованием
100 МБ исчезло.

## Почему UTF-16, а не UTF-8

Первая редакция этого ADR предписывала хранить UTF-8. Это ошибка для JVM.

Строки на JVM — UTF-16, а отрисовка идёт 60 раз в секунду и требует `String`: хранение
UTF-8 означало бы декодирование на каждом кадре. Парсинг же происходит редко и в фоне.
Оптимизируем горячий путь, конвертацию делаем на границе с парсером — один раз за парс.
Побочная выгода: координаты LSP считаются в UTF-16, и конвертация там становится не нужна.

## Цена

- Rope проигрывает плоскому массиву на линейном сканировании (поиск по файлу, сохранение).
- Реализация дерева требует property-тестов: без них редкие баги на границах чанков и на
  суррогатных парах гарантированы. Тесты сравнивают rope с `StringBuilder` на детерминированной
  псевдослучайной последовательности правок и проверяют инварианты дерева после каждого шага.
- Офсеты снаружи не должны разрезать суррогатную пару. Внутренние разрезы (нарезка на листья)
  пару не рвут — за этим следит отдельная проверка.

## Файлы больше порога

Открываются read-only с явным предупреждением. Это несколько десятков строк, а не отдельный
режим редактора.
