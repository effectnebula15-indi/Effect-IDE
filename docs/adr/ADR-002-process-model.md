# ADR-002. Код пользователя исполняется в отдельном процессе

## Контекст

Требования: остановить бесконечный цикл, пережить падение пользовательского кода, не
накапливать утечки. Простейший вариант — вызвать интерпретатор через JNI в фоновом потоке
процесса IDE.

## Почему простейший вариант не работает

- Прервать `while True: pass` в CPython можно только асинхронным исключением, которое
  срабатывает на границах байткода. Если код завис внутри C-функции, оно не сработает.
- `segfault` в любом C-расширении убьёт IDE вместе с несохранённым текстом.
- Память, не возвращённую интерпретатором системе, процесс IDE будет держать до конца жизни.

## Решение

Пользовательский код исполняется в отдельном процессе. На Android — второй процесс того же
APK (`android:process=":runner"`, штатная возможность платформы, не хак). На Desktop —
обычный дочерний процесс.

## Последствия

- Принудительное завершение становится надёжным: `Process.killProcess`.
- Падение раннера не трогает IDE.
- Тот же процесс потом хостит WASM-рантайм и нативный код — `ExecutionBackend` не переделывается.
- Лимит памяти ставится в раннере до старта интерпретатора.

## Цена

Протокол IPC и его сериализация — код, которого иначе бы не было. Плюс 20–40 МБ памяти на
второй процесс. Отладка двухпроцессной системы заметно неприятнее однопроцессной.

## Чего это решение НЕ даёт

Изоляции файловой системы. Без root на Android нет `chroot`, а seccomp-bpf для v1 слишком
дорог. Раннер стартует с `cwd` и `HOME` в папке проекта, и мы полагаемся на то, что код свой.
Настоящая песочница появится только вместе с WASM-бэкендом.

## Лимиты: надзор снаружи, а не setrlimit (уточнено в P4)

Первая редакция предполагала `setrlimit(RLIMIT_AS)` внутри раннера и честно отмечала риск:
лимит ставится в процессе, где уже поднят ART, и способен убить сам рантайм раньше
пользовательского кода. Проверять эту гипотезу оказалось дороже, чем обойти её.

Решение: **лимиты соблюдает сторож в процессе IDE.** Он знает pid раннера (тот присылает
его сообщением `Started` сразу после запуска), опрашивает `/proc/<pid>/statm` и при
превышении времени или памяти убивает процесс через `Process.killProcess`.

Что это даёт:
- ошибки «лимит убил не тот код» не существует в принципе;
- механизм одинаков для любого будущего бэкенда, не только для CPython;
- остановка по кнопке — тот же путь, что и по лимиту, а не отдельная ветка.

Цена, названная прямо:
- реакция не мгновенная — в пределах интервала опроса (по умолчанию 250 мс);
- считается RSS всего процесса раннера, а не только объектов Python: интерпретатор
  и стандартная библиотека входят в эту цифру, и порог надо задавать с их учётом;
- на устройствах с 16-килобайтными страницами константа 4096 дала бы четырёхкратную
  ошибку, поэтому размер страницы спрашивается у системы.

Почему остановка — именно убийство процесса, а не просьба завершиться: программа в
`while True` свой канал не читает, а прервать её изнутри интерпретатора надёжно нельзя —
ровно по тем причинам, по которым и понадобился отдельный процесс.
