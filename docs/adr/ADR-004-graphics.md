# ADR-004. Графика: собственный Canvas API поверх разделяемой памяти

## Решение

Программа пользователя рисует через наш Canvas API. Кадр пишется в разделяемую память,
IDE забирает его и выводит в `SurfaceView` (Android) или Skia Canvas (Desktop).
Уровни SDL2, OpenGL ES и встроенный X11 в v1 не делаются.

## Два следствия, определяющие форму API

**Canvas имеет собственное логическое разрешение, по умолчанию не равное экрану.**
Кадр 1080×1920×4 — это 8 МБ; при 60 fps только копирование даёт полгигабайта в секунду.
Флагман переживёт, дешёвый телефон нет. Значение по умолчанию порядка 480×800 с
масштабированием при выводе; настраивается.

**API батчевый, не по-пиксельный.** Обёртка для Python идёт через `ctypes` — а не
C-расширением, иначе пришлось бы пересобирать под каждую версию Python. Вызов через `ctypes`
стоит микросекунды, поэтому `set_pixel` в двойном цикле неработоспособен. Примитивы принимают
массивы: `draw_lines(points)`, `blit(buffer)`, `fill_rect(...)`.

## UX на телефоне

Графическое окно занимает весь экран. Свайп возвращает к коду, **программа при этом
продолжает работать**: кадры живут в разделяемой памяти, а `Surface` — только потребитель,
поэтому его уничтожение при уходе с экрана программу не останавливает.

Чего схема не переживёт: сворачивания приложения целиком — Android вправе убить процесс
раннера. Foreground-сервис с постоянным уведомлением в v1 не делаем, показываем честное
«программа остановлена системой».

## Отложенная оптимизация

Раннер мог бы писать прямо в `Surface` через `ANativeWindow` без копирования (`Surface`
передаётся между процессами). Отложено: требует Binder/AIDL и ломает единообразие с
удалённым бэкендом, где кадры всё равно идут по сети. Вернёмся, если не хватит fps.
