# Правила проекта

Файл для Claude Code и для человека, вернувшегося к проекту через месяц.

## Границы, которые нельзя нарушать

Проверяются задачей `./gradlew checkArchitecture`, правила лежат в корневом `build.gradle.kts`.

- `:core` — чистый Kotlin/JVM. Ни Compose, ни Android, ни Skia, ни JNI. Только Kotlin stdlib
  и kotlinx. Причина: этот код должен тестироваться обычными JVM-тестами без эмулятора —
  это единственные тесты, которые можно гонять на любой машине.
- `:core` зависит только от `:platform:api`, никогда от конкретных реализаций.
- `:runner` не знает про `:ui` вообще — это отдельный процесс, связь только по протоколу.
- Тяжёлые внешние библиотеки живут в своих модулях, а не в `:core`. Git — в `:vcs`
  (ADR-006): иначе JGit поехал бы и в процесс-раннер, которому git не нужен.
- `:app:*` — точка сборки, ей можно всё.

Если граница мешает — правило меняется вместе с ADR, а не обходится в модуле.

## Байткод исполняется и на Android

Модули `:core`, `:platform:api`, `:runner` компилируются с `jvmTarget = 17` и
`-Xjdk-release=17`. Это не формальность: `InputStream.readNBytes` есть в Java 9, но на
Android только с API 33, а minSdk у нас 27. Такая ошибка вылезает не на сборке, а на
устройстве у пользователя.

## Что проверяется где

- Ядро, протокол, логика — JVM-тесты, гоняются везде, в том числе в CI.
- Нативный код (`native/`) — на хосте под ASan/UBSan и TSan (`./gradlew checkNative`),
  тоже в CI. Ошибки двухпроцессного C не воспроизводятся по требованию, и ловить их
  на телефоне — самый дорогой способ. Чего санитайзеры на x86 не поймают: снятый
  барьер памяти. Это проверяется только на ARM, то есть на телефоне.
- Всё, что касается реального устройства (fps, ANR, W^X, память, тач, разделяемая память)
  — только на настоящем телефоне. Эмулятор в CI и в агентских сессиях недоступен.
- Каждая фича сначала доводится на десктопе, потом переносится на Android.

## Стиль

- Комментарии только там, где неочевидно **почему** так сделано. Что делает код, видно из кода.
- Когда решение имеет цену — цена называется в комментарии или в ADR, а не умалчивается.
- Русский в комментариях и документации, английский в идентификаторах. **Имена
  тест-методов — тоже идентификаторы.** Русские имена в обратных кавычках ломают сборку
  на машине с неюникодной локалью: Gradle пишет HTML-отчёт в файл с этим именем, а JVM
  кодирует имена файлов по `sun.jnu.encoding`, а не по `file.encoding`. Пояснения
  по-русски живут в сообщениях проверок и в комментариях — там от них больше пользы.
- Новый модуль сопровождается коротким разбором в `docs/modules/`.

## Android

- `compileSdk` 37.2, `targetSdk` 36, `minSdk` 27, только ABI `arm64-v8a`.
- С AGP 9 поддержка Kotlin встроена в сам AGP: плагин `org.jetbrains.kotlin.android`
  применять не нужно и нельзя.
- CPython скачивается на сборке с python.org и сверяется по sha256; в репозитории его нет.
- **Lint здесь не формальность.** Он уже поймал две ошибки, которые иначе вылезли бы
  только на телефоне: нерезолвящийся класс активности в манифесте и вызов API 28
  при minSdk 27. `./gradlew build` гоняет lint, отключать его нельзя.

## Ловушка окружения: кодировка имён файлов

`sun.jnu.encoding` — это НЕ `file.encoding`. С Java 18 второй по умолчанию UTF-8, а имена
файлов по-прежнему кодируются по локали, и при `LANG=POSIX` получается ASCII. Тогда JVM
записывает «заметки.txt» на диск как «????????.txt»: файл создаётся, но открыть его по
исходному имени уже нельзя.

На Android этого не бывает — там имена всегда UTF-8. Это настольная беда, и лечится она
запуском с юникодной локалью (`LANG=C.UTF-8`), а не из кода: `sun.jnu.encoding` читается
при старте JVM. Десктопное приложение проверяет это на старте и предупреждает.

## Версии

Для сборки нужен Android SDK (платформа 37.2, build-tools 36, NDK 29.0.14206865) —
путь к нему в `local.properties`, который в git не попадает.

Все версии — в `gradle/libs.versions.toml`. Gradle-плагины подключаются только в
`build-logic`: если модуль объявит плагин с версией сам, Kotlin-плагин загрузится дважды.
